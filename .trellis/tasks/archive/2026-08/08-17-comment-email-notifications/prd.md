# 博客评论邮件通知

## Goal

为博客评论生命周期增加邮件通知，让评论者及时得知审核结果，并让管理员及时得知站点内容收到了新回复。

## Background

- 邮件发送能力由上游 SSO 提供，Applog 调用其第三方通知接口。
- 上游集成文档：<https://sf.imouto.tech/third-party-notification-integration-guide.html>
- 当前评论状态包含 `pending`、`approved` 和 `rejected`。

## Confirmed Facts

- 游客提交评论时必须提供昵称和邮箱，评论初始为 `pending`；已登录用户的评论初始为 `approved`。
- 管理员审核可将评论设为 `approved` 或 `rejected`，当前服务会直接保存传入状态，未区分“状态未变”。
- 评论可以指向文章或独立页面，也可通过 `parentId` 回复已公开的父评论。
- 文章保存作者用户 ID；系统用户保存邮箱、角色、可空的旧 SSO 数字 ID，以及 OIDC issuer/subject。
- 上游创建通知为 `POST /v1/notifications`，使用 `Authorization: NotificationKey <value>`；创建成功只表示已入队。
- 上游收件人支持 H 数字用户 ID 或手动 Email；模板和直接内容都受 H 策略授权。
- 上游支持 1–191 字符的幂等键、异步状态查询，并对 `429`/`503` 建议复用幂等键限次退避重试。

## Requirements

- 游客或已登录用户提交的评论在状态变化时，向评论者发送结果通知。
- 仅在持久化状态值真正改变时发送评论者通知，覆盖 `pending -> approved`、`pending -> rejected` 以及后续 `approved <-> rejected`；重复设置当前状态不发送。
- 游客评论者使用提交时的 `guestEmail`，通过 H 的 `kind: "email"` 收件人发送。
- 已登录评论者通过 H 的 `kind: "user"` 收件人发送，`userId` 取本地用户的 `ssoId`。
- 若已登录收件人的 `ssoId` 为空，不回退到 Email：跳过该收件人并记录不包含个人信息的告警。
- 站点文章或独立页面收到新评论时，向管理员发送通知。
- “新评论”包括顶层评论和带 `parentId` 的嵌套回复，在评论创建成功后触发，不等待审核通过。
- 新评论通知的收件人为所有管理员；不因文章/页面作者身份额外发送。
- 管理员自己提交的评论不触发管理员新评论通知。
- 邮件由服务端通过上游 SSO 通知接口发送。
- 上游 SSO 新签发的 mail token 必须作为独立系统配置保存在数据库，不依赖部署环境变量传入凭证。
- 通知配置包含 `mailToken` 和 `enabled`；仅在已启用且 token 存在时发送。
- mail token 仅服务端可读；管理员专用读取接口只返回脱敏占位，保存时空值或脱敏占位表示保留原 token。
- mail token 沿用现有 Umami/Duolingo 凭证模式，以明文存入 `SystemConfigEntity` 的配置 JSON；数据库与备份必须由运维访问控制保护，泄露时通过 H 吊销并重签 token。
- 通用系统配置读写接口不得读出或覆盖通知密钥配置；专用配置接口只允许管理员访问。
- 管理后台“系统设置”中新增独立的“评论邮件通知”配置区，包含启用开关和密码型 token 输入，仅管理员可见。
- 使用 H 托管的 `applog-comment-status` 和 `applog-new-comment` 模板发送；Applog 通知请求只提交模板键和最少必要变量。
- `applog-comment-status` 变量覆盖评论者显示名、目标标题、目标类型、审核结果、纯文本评论摘要和查看链接。
- `applog-new-comment` 变量覆盖站点名、目标标题、目标类型、评论者显示名、纯文本评论摘要和后台管理链接。
- 模板不接收 IP、邮箱、User-Agent、身份凭证或其他非必要隐私数据；评论摘要必须限长且作为纯文本处理。
- 两份邮件模板的 HTML 和变量契约必须存放在仓库中，纳入版本控制和评审。
- 仓库中的 HTML 是 H 后台模板的权威版本化来源，通过人工流程发布到 H。
- 评论创建或审核状态先成功持久化；通知失败不回滚、不改变原业务接口的成功结果。
- 每个通知事件使用由事件类型和不可变业务标识组合的稳定幂等键；网络异常、`429` 和 `503` 仅在当前请求内做有限次带退避的重试，并复用同一幂等键。
- 最终失败时记录脱敏错误和可追踪的评论/事件标识，不记录收件地址、Authorization Header 或通知正文。

## Acceptance Criteria

- [ ] 评论审核状态发生符合产品规则的变化时，有可观察的邮件通知尝试。
- [ ] `pending -> approved/rejected` 和 `approved <-> rejected` 会通知评论者；状态值未变时不发送。
- [ ] 游客收件人使用 `guestEmail`；已登录用户收件人使用 H 用户类型和本地 `ssoId`。
- [ ] 已登录收件人的 `ssoId` 为空时，不发送且不泄露邮箱或其他个人信息，服务端产生可观察告警。
- [ ] 非管理员在文章或独立页面创建顶层评论或嵌套回复成功后，所有管理员收到包含必要上下文的邮件通知。
- [ ] 管理员自己创建的评论不产生管理员新评论通知。
- [ ] 邮件接口失败时的业务行为有明确规则，且可通过测试验证。
- [ ] 通知失败不回滚已成功的评论创建或状态更改，也不将通知失败暴露为评论业务失败。
- [ ] 可恢复失败在有限重试中复用稳定幂等键；不可恢复失败不重试；最终失败产生脱敏可观察日志。
- [ ] 两类通知使用约定的 H 模板键与变量，且请求中不含邮箱、IP 或 User-Agent 等非必要隐私变量。
- [ ] 仓库包含 `applog-comment-status` 和 `applog-new-comment` 的 HTML 模板及变量契约，两者与服务端发送的变量保持一致。
- [ ] 管理员可在系统设置页读取脱敏状态、更换 mail token 并启用/停用评论邮件通知，不需要重新构建前端或修改部署环境。
- [ ] 管理员读回配置时 token 始终脱敏；空值/脱敏占位保存时保留原 token，新值则替换原 token。
- [ ] 服务端能从数据库读取完整 mail token 完成 H 认证，但任何 API 响应、前端状态或日志都不包含明文 token。
- [ ] 非管理员不能读写通知配置，通用配置接口也不能泄露或覆盖 mail token。
- [ ] `enabled` 为假或 token 缺失时不向 H 发起请求，且不影响评论创建或审核成功。

## Out of Scope

- 在 Applog 内自建 SMTP 或邮件投递基础设施。
- 修复 OIDC 用户的 `ssoId` 写入、补齐存量用户或设计新的外部身份映射。
- 持久化通知 outbox、后台重试 worker、异步投递状态轮询或“最终必达”保证。
- 自动创建、更新或发布 H 邮件模板。
